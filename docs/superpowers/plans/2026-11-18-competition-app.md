# 출하 신호등 대회 제출본 개발 계획

> 에이전트 실행 지침: 계획을 사용자와 검토한 다음 `superpowers:executing-plans`로 작업별 실행한다. 코드를 수정하면 code-reviewer 서브에이전트의 리뷰를 받고 지적을 반영한다. 현재 문서는 계획이며 구현·검증 완료 기록이 아니다.

**목표:** 비전문가가 센터 PC에서 실행하고 실제 도매 자료의 가격·비교 근거를 확인할 수 있는 AI Agent와 재현 가능한 제출물을 완성한다.

**아키텍처:** 기존 React·FastAPI·CSV 캐시·규칙 판단 구조를 유지한다. 데이터 수집과 조회를 분리하고, 계산은 Tool이 담당하며 Agent가 의도에 따른 Tool 선택·자료 상태 판단·대체 경로를 수행한다. Android는 같은 화면을 공유하며 외부 공개 배포는 후속 단계로 둔다.

**기술:** Python 3.10 이상, FastAPI, pandas, React, TypeScript, Vite, Capacitor, pytest, GitHub Actions를 사용한다. 기존 패키지 관리와 구조를 유지한다.

**근거:** [공식 대회 안내](https://daker.ai/public/hackathons/jeju-ai-bigdata-agent-challenge)를 2026-11-18 확인했다. 현재 구현은 `HANDOVER.md` 상단·`README.md`·`docs/MOBILE.md`와 대조했다. `docs/READINESS.md` 본문은 11/15 기록으로 이미 해결한 항목이 섞여 있다.

## 1. 공식 요구사항과 개발 방향

- 공식 마감은 2026-11-20 10:00 KST다. 이후 제출·수정이 불가능하다.
- 제주빅데이터센터 또는 제주데이터허브 데이터 1종 이상을 실제 사용해야 한다.
- 필수 제출물은 15페이지 이내 AI Agent 기획서와 최종 결과물 ZIP이다. ZIP에는 소스, 환경·매뉴얼, 데이터 활용 명세, 결과 설명자료가 필요하다.
- 센터 최소 사양은 i7-8700, GTX 1060, RAM 32GB, VRAM 3072MB다. 공식 게시판의 Windows 11 26H2·인터넷·확장 모듈 허용 조건을 적용하고 실제 설치를 별도 검증한다.
- AI 모델·사용 범위, 외부 API·서비스·데이터·코드를 공개하고 데이터 이용조건을 확인해야 한다.
- 위 요구로부터 1차 목표를 대회 제출·센터 시연으로 정한다. 일반 사용자 배포·스토어 출시는 2차 목표다. 이는 개발 우선순위 판단이며 대회가 모바일을 금지한다는 뜻은 아니다.
- 공식 평가표와 운영자 Q&A를 재확인했다. 전문가 70%, 기획서 ELO 30%다. 항목별 배점과 동점 기준, 수정 일정은 [모의 심사 기록](../../JUDGING_REVIEW.md)을 따른다.

## 2. 제품 요구사항 초안

주 사용자는 IT에 익숙하지 않은 농가·도민이다. 핵심 과업은 품목을 누르고 최근 거래 가격, 비교 기준, 신호 이유, 자료의 한계를 읽는 것이다. 실제 출하 지시나 수익 보장을 제공하지 않는다.

| 구분 | 이번 범위 | 완료 기준 |
| --- | --- | --- |
| Must | 검증한 기본 품종 조회 | 당근부터 검증하고 가능한 5품목으로 확대한다. 미검증 품목은 추천·데모에서 제외하고 상태를 밝힌다. |
| Must | 가격·최근 추세·전년 비교·신호 근거 | CSV에서 별도 계산한 결과와 API·화면이 일치한다. 자료 부족이면 해당 계산을 생략하고 이유를 표시한다. |
| Must | 실제 Agent 흐름 | 의도 분기, Tool 선택, 휴장일 대체, 자료 부족 처리, trace를 입력·출력 사례로 증명한다. 규칙 처리와 LLM 처리를 구분한다. |

| Must | 센터 실행·제출 자료 | 매뉴얼만 보고 새 환경에서 실행하고 공식 제출 항목을 모두 갖춘다. |

| 후속 | 스토어 배포·사용자 계정·푸시 | 별도 요구사항과 운영 계획으로 진행한다. |

LLM은 현재 기본값 `none`을 유지한다. 선택 LLM을 제출 범위에 넣으려면 오류 시 fallback과 숫자·신호 일치 검증을 별도 통과해야 한다. 무거운 로컬 모델 탑재는 이번 필수 경로로 두지 않는다.

## 3. 공통 작업 기준

- Git 작성자는 rokmc1893으로 유지한다. 공동 작성자 트레일러를 추가하지 않는다. AI 사용 내역은 사실대로 남긴다.
- 키·개인정보·브라우저 프로필·에뮬레이터 데이터·개발 캡처는 Git과 제출 ZIP에서 제외한다. 공식 안내의 평가용 AI 키 예외를 기본 채택하지 않는다.
- 운영자 답변에 따라 공개 허브 1361 스냅샷은 심사용 ZIP에 포함한다. 공개 Git에는 CSV를 넣지 않는다. 키 발급·갱신 절차를 매뉴얼에 둔다.
- 새로운 사용자 계정·데이터베이스·프레임워크를 추가하지 않는다.
- 코드 작업마다 재현 또는 실패 테스트 → 최소 수정 → 관련 테스트 → code-reviewer → 수정 반영 → 커밋 순서를 따른다.
- 전체 pytest·프론트 빌드·필요 플랫폼 검사를 릴리스 후보에서 실행한다. 고치지 않은 P0/P1 또는 필수 경로 실패가 있으면 완료로 표시하지 않는다.
- 로그·실험 원본은 Git 제외 `outputs/validation/`에 둔다. 제출 문서에는 키·개인정보를 제거한 표와 결과만 기록한다.
- 기존 99개·CI 6개 통과는 11/17의 기록이다. 이번 계획 작성 중에는 테스트를 다시 실행하지 않았다.

### 완료의 정의와 역할

기능 완료는 코드가 존재하는 상태가 아니다. 요구사항 충족, 실제 또는 통제된 입력의 검증, 회귀 검사, 코드 리뷰, 오류·제약 문서, 실행 방법이 모두 갖춰져야 한다. 데이터 미확인·기기 미실행은 미확인으로 남긴다.

- P0는 자료 손상·비밀정보 노출·필수 실행 불가다. 즉시 중단하고 먼저 고친다.
- P1은 잘못된 가격·품목·단위·신호 또는 필수 과업의 실패다. 릴리스 전에 고친다.
- P2는 우회 가능한 불편·비필수 기능 결함이다. 영향과 우회를 기록하고 범위를 조정한다.
- Codex는 구현·자동 검증·문서를 맡고 code-reviewer는 코드 변경을 독립 검토한다. 소민님은 제품 범위 검토·실사용 확인·계정이 필요한 제출을 맡는다. Claude의 추가 작업은 구체적인 산출물이 필요할 때만 분리한다.
- 각 요구사항에 식별자와 검증 결과를 연결한다. 예: R-가격 → 작업 2·3 → 기준 가격 비교표 → PASS/FAIL/미실행이다. `docs/SUBMISSION_REQUIREMENTS.md`에 이 표를 둔다.

## 4. 우선 점검할 실패 조건

1. 휴장·갱신 지연·부분 캐시를 최신 시세로 오인하지 않아야 한다. 작업 3·4가 검증한다.
2. 품종·kg 단위·전년 비교 날짜가 달라도 정상 비교처럼 보이지 않아야 한다. 작업 2·3이 검증한다.
3. 허브 오류·쿼터 소진·강제 중단 후 원자료를 잃거나 수집 완료로 표시하지 않아야 한다. 작업 2가 검증한다.
4. 연속 터치·네트워크 끊김에서 이전 응답이 새 선택을 덮지 않아야 한다. 작업 4가 검증한다.
5. 개발 맥·외부 LLM·개인 키 없이 새 PC에서 실행하는 경로가 문서와 맞아야 한다. 작업 5·6이 검증한다.

### 작업 2. 당근 데이터 가능성·수집 검증 — G1

대상은 `config/items.yaml`, `scripts/collect.py`, `scripts/validate_cache.py`, `backend/tests/test_collect.py`, `docs/DATA_VALIDATION.md`(신규)다. 데이터는 `data/cache`에 두고 Git에서 제외한다.

입력은 `.env` 허브 설정과 기본 품종 당근(일반)이다. 출력은 검증 보고서와 재사용할 캐시다.

- [x] 상태·당일 예산·기존 자료를 먼저 확인한다. 실수집은 오늘 호출 원장에 반영하며 실 API를 테스트에서 반복 호출하지 않는다.
- [x] `.venv/bin/python scripts/collect.py --no-weather --item carrot --default-only`로 수집하고 종료 코드·실패 구간·행 수·기간을 기록한다.
- [x] `.venv/bin/python scripts/validate_cache.py --item carrot --default-only --json`을 실행한다. 오류 0건을 목표로 하고 경고는 원인·영향·처리를 모두 기록한다. 날짜 공백을 임의로 정상 처리하지 않는다.
- [x] 단위와 도매 자료의 의미를 원천 설명으로 확인한다. 단위가 불명확하면 환산 기능을 제한하는 결정을 문서화한다.
- 해당 없음(이번 수집 실패 0건). 실제 실패가 있으면 비밀정보 없는 가짜 응답으로 재현 테스트를 만든 뒤 수정·리뷰한다. 기상 수집이 핵심 거래 검증을 막지 않게 분리한다.

G1은 당근의 기간·품종·중복·결측·단위·최신일과 실패 구간을 설명할 수 있으면 통과한다. 자료가 부족하면 기능 범위를 줄이고 다음 단계에서 그 사실을 표시한다.

### 작업 3. 계산·Agent 통합 검증과 품목 확대 — G2

대상은 `backend/app/tools.py`, `backend/app/judge.py`, `backend/app/agent.py`, `backend/tests/test_core.py`, `backend/tests/test_readiness.py`, `docs/DATA_VALIDATION.md`다. 변경은 검증에서 발견한 결함에 한정한다.

기존 인터페이스 `AgentRequest` → `Agent.run()` → `AgentResponse.as_dict()`, HTTP `POST /api/ask`, `GET /api/health`, `GET /api/items`를 유지한다.

- [x] 원자료에서 기준일 가격·7/30거래일 평균·전년 비교를 별도로 계산해 기존 Tool 결과와 대조한다. 날짜·단위는 정확히 일치하고 숫자는 화면 표시 자리에서 일치해야 한다.
- [x] `test_reference_prices_across_observation_windows`에 비밀정보·재배포 제한이 없는 고정 fixture와 독립 계산 기대값을 둔다. 실제 CSV 전체를 회귀 테스트에 커밋하지 않는다.
- [x] `test_reference_prices_across_observation_windows`로 직전 거래일·전년 자료 없음·계산 불가 안내를 확인한다. 기존 테스트가 같은 조건을 충분히 검증하면 중복 추가하지 않는다.
- [x] 실제 입력 → 선택한 Tool → 결과 → 신호 조건 → 화면 문구를 대조한다. 버튼 경로 LLM 호출 0회를 확인한다.
- [x] 당근 통과 후 월동무·양배추(일반)·깐마늘·조생양파를 같은 표로 검증한다. 기본 품종만 먼저 수집한다.

### 작업 5. 센터 실행·기기 검증 — G4

대상은 `start.sh`, `start.bat`, `requirements*.txt`, `docs/MOBILE.md`, `docs/INSTALLATION_TEST.md`(신규)다.

- [ ] 깨끗한 설치 환경에서 README만 보고 설치 → 수집 또는 허용된 캐시 준비 → 실행 → 핵심 조회 → 재시작을 검증한다. Windows GitHub 테스트 통과를 센터 설치 검증으로 대체하지 않는다.
- [ ] 최초 설치·수집은 인터넷이 필요하다는 점과, 캐시 조회에 외부 서비스가 필요한 범위를 분리해 기록한다. 센터 OS·권한을 못 확인하면 그 한계를 명시한다.
- [ ] 30분 반복 조회 중 오류와 품목 응답 시간을 기록한다. 로컬 캐시 버튼 조회 p95 3초 이내를 프로젝트 목표로 두고 PC 사양·측정 횟수를 함께 기록한다. 공식 대회 성능 기준이라는 표현은 쓰지 않는다.
- [ ] 갤럭시 에뮬레이터에서 기존 설치 앱의 핵심 조회를 확인한다. 아이폰 실행은 런타임이 준비되면 확인하되 미확인 상태로 iOS 지원 완료를 주장하지 않는다.
- [ ] 평가 시 접근 가능한 서버 또는 센터 로컬 실행 경로를 문서대로 재현한다. 맥 개발 서버 의존 APK를 일반 배포본으로 제공하지 않는다.

G4는 제출 대상 PC의 재현 경로와 의존성을 확인하면 통과한다. 센터 환경에 접근할 수 없으면 G4를 미확인으로 남기고, 대체 Windows 환경의 검증 결과·남은 위험을 명시한다. 사용자와 축소 제출 여부를 결정하며 센터 검증 완료로 바꾸지 않는다.

### 작업 6. 필수 제출물·릴리스 후보 — G5

신규 문서는 `docs/DATA_USAGE.md`, `docs/RESULTS.md`, `docs/USER_GUIDE.md`, `docs/SUBMISSION_CHECKLIST.md`다. 기획서 파일은 `submission/`에 두되 개발 캡처·키는 포함하지 않는다. ZIP은 Git 제외 `outputs/submission/`에 생성한다.

- [ ] 기획서 원본을 확보한다. 없으면 위 문서를 기준으로 다시 작성하고 15페이지 이내를 확인한다.
- [ ] 데이터별 출처·항목·기간·이용조건·전처리·실제 사용 여부와 외부 코드·라이브러리·AI 사용 내역을 작성한다.
- [ ] 실제 검증 결과만 결과 설명자료에 넣는다. 합성 시연은 명확히 표시한다. trace와 규칙·선택 LLM의 역할을 구분한다.
- [ ] 사용 매뉴얼에 키 발급·환경변수 예시·오류·자료 갱신·제약·센터 활용 방법을 작성한다.
- [ ] 릴리스 후보 커밋을 정하고 전체 pytest·프론트 빌드·GitHub CI를 확인한다. 실행하지 못한 검사와 남은 결함을 기록한다.
- [ ] ZIP 항목 목록을 검사해 필수 파일 누락·키·`.env`·브라우저/에뮬레이터 데이터·개발 캡처·배포 금지 데이터를 제외한다. 압축을 새 폴더에 풀고 설치·실행 절차를 재검증한다.

G5는 필수 제출 항목과 내용이 실제 실행 결과와 일치하고 패키지를 새 폴더에서 재현하면 통과한다.
